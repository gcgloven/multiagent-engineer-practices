# Contributing

Keep changes tied to a demonstrated task, learning need, or failure. Include a representative example showing why a rule, role, or method is useful. Preserve direct assignment, open inquiry, and meaningful depth.

For prompts and skills, review triggers, method substance, learning checkpoints or completion conditions, authority, evidence quality, and unnecessary repetition. New profiles need a distinct responsibility or perspective that improves the work. New methods need actionable steps and judgment criteria, not headings alone. Avoid copying the shared contract into every source file. Use the [skill design guide](docs/skill-design.md).

Run `python3 -B scripts/prepare.py` after editing profiles, skills, or squad policy. Inspect the generated prompts and full skill archives; `build/` is disposable and ignored. Validate skill frontmatter and relative links. For behavior changes, exercise a realistic scenario and report what was actually checked, including whether Multica dispatch was executed. Runnable checks are listed in [VALIDATION.md](VALIDATION.md).

Keep credentials, workspace identifiers, raw user conversations, execution logs, and private project examples out of contributions. Use generic or explicitly shareable evidence. Preserve source attribution when adapting external material.

Store local audit records and project-specific evidence in the ignored `obsolete/` folder. Follow the [publication checks](docs/publication.md) before sharing a source archive or changing repository visibility.

Pilot before claiming faster or cheaper operation. Compare task outcomes and avoidable coordination as well as actual usage. Prefer evidence quality and useful progress over prompt word-count targets or the fewest possible agents.
