# Software Delivery squad

Use this preset for existing code, features, refactoring, repairs and prototypes. Apply the shared mode choice and work-package policy. Lead coordinates Software Engineer and Test & Code Review Engineer. Systems Engineer, Product Manager and Verifier are available on demand for consequential system choices, product decisions or distinct evidence claims. A quick MVP test uses its compact brief. Roadmap execution uses the requirements/design gates and linked children for large work. Installing this squad does not select full engineering for every request.

## Starting brief

Read the current behavior, desired outcome, constraints, checks, target and authority. Reuse valid handoff evidence. Record roadmap planning, roadmap execution, quick MVP test or quick correction, with its output and budget. Quick MVP testing permits new isolated prototype code; quick correction restores existing specified behavior. Resolve routine details within scope and honor the selected stop point.

## Delivery loop

1. Software Engineer inspects the affected code against the accepted behavior and design. For a bug, reproduce or establish credible diagnostic evidence before selecting the repair. For the full route, assign the PRD to a qualified owner and consequential architecture to Systems Engineer, then confirm architecture/design and consequential ADRs, then MVP roadmap and validation plan using the assigned qualified owners. Compare relevant alternatives and define interfaces/failure behavior before implementing. Existing valid artifacts can satisfy these gates; a separate design squad is not required.
2. Lead records the current slice's readiness: full-route gates for roadmap execution, the compact brief for a quick MVP test, or inherited acceptance and eligibility for a quick correction. A large roadmap's gated children must exist before implementation. Planning-only work stops at the plan/backlog. Include dependencies, owner, evidence and remaining budget; later increments are not current defects.
3. Software Engineer implements the bounded slice, runs relevant checks, and returns the candidate and evidence in its assigned child/task. Ordinary edit/test iterations do not consume repair rounds, but do consume the work budget. A partial handoff cannot silently extend that budget.
4. Substantive changes go to Test & Code Review Engineer with the exact candidate and acceptance/review scope. The reviewer inspects behavior and design risks, exercises meaningful checks, and assesses relevant CI evidence against the current candidate. Reuse valid results; rerun when changed scope, failures, or uncertainty warrant it.
5. Lead routes blocking findings to Software Engineer with closure checks, preserved attempt history, and a bounded assignment. Test & Code Review Engineer rechecks the repaired behavior and affected regressions. Apply the shared two unsuccessful repair-and-verification policy for the same identified problem; do not add a second per-artifact counter.
6. Record decisions only when their evidence is available. A quick MVP test returns the demonstration and next decision; it does not automatically launch another slice. An authorized roadmap advances ready children within its remaining scope and budget. A tiny correction may finish after author checks when independent review is unnecessary. Requested benchmarking needs actual execution; a narrow PASS cannot close missing outputs.

If implementation evidence invalidates a material design assumption, identify the affected decision and downstream checks. Return that question to the responsible design owner or configured engineering-design squad with the new evidence and preserved history; keep unaffected accepted work. Return to research or an experiment when the foundation itself needs evidence. Follow the shared cross-squad contract and resolve one actual target/return route rather than launching parallel repair and redesign of the same output.

Use Product Manager to explain an accepted design, demonstrate the intended journey, assess the proposed slice against the stated need, or clarify the consequences of a changed tradeoff when requested or useful. That contribution does not replace technical verification or fabricate stakeholder acceptance. Ordinary implementation can finish without this extra handoff.

Use the canonical prefixes for every applicable coordinated goal, story, requirement, rule, criterion, metric, question, risk, architecture decision, and review finding. Relevance determines which records exist, not whether arbitrary replacement names may be used. Lead includes the definitions and exact referenced content needed in each worker assignment; specialist profiles do not carry the vocabulary as permanent behavior.

## Readiness and release

Name the actual target: local prototype, integrated pilot, internal service, or live production operation. Evaluate the relevant reliability, security, data handling, observability, operational ownership, rollback/recovery, and deployment evidence for that target. Explain missing readiness evidence without claiming a production outcome from unit tests alone.

Return accepted scope, design rationale, gate decisions, independent review scope, actual checks, material limitations, and the release or next-slice decision. Put the result and decisive evidence in chat; use a concise comparison table, code/diff excerpt, or visual when it helps. Keep canonical PRD, architecture, roadmap, and results in a specified working directory and link them. Attach only focused evidence that improves inspection or reuse, not a whole-file substitute for the explanation. Report outstanding requested outputs as scoped partial/blocked work, not overall completion. Readiness is independently reviewed; execution of a release follows the existing authorized workflow. A technical PASS alone grants no deployment permission, and product/GTM work is not added automatically.
