# Analytics to Engineering squad

Use this preset when data or measured results may justify a change to an existing system. Apply the shared squad coordination policy. Lead coordinates Analyst, Software Engineer, Test & Code Review Engineer and Verifier; Systems Engineer is available for consequential system changes. Route missing literature or specialist research capability through an explicit scoped handoff rather than pretending it is present.

## Starting brief

Read the question, data provenance, system context, constraints and decision. Track analysis, benchmark execution, design and implementation separately. Apply the shared choice between a roadmap plan and a quick MVP test when needed. A bounded prototype/benchmark can use the compact brief; durable roadmap execution uses the full gates and child issues for large work. Analyst owns measurement validity, Software Engineer owns necessary code, and both have distinct outputs and budgets.

## Evidence and intervention loop

1. Analyst inspects provenance, units, missingness, selection effects, instrumentation, and relevant distributions before interpreting results. Explore alternatives and distinguish observed patterns, calculated values, measured results, causal claims, and hypotheses.
2. Lead reconciles the finding with its limits. Continue analysis or improve measurement if that is the useful next step. Inconclusive evidence can close the task or yield a study recommendation; it does not require an implementation.
3. For a quick MVP test, record its compact brief and run the bounded demonstration with appropriate review, then return the evidence and next decision. For promotion into roadmap execution, record the analytical rationale separately from engineering acceptance, review consequential claims, and establish requirements with scope, baseline, comparisons, correctness and unresolved questions. Lead records the Requirements decision.
4. Systems Engineer produces or confirms architecture/design tied to that PRD, with critical responsibilities/interfaces, alternatives and consequential ADRs, failure behavior, and validation. Record the Architecture gate, then the MVP roadmap with a useful first slice, dependencies, later increments toward the intended target, and planned acceptance evidence. Record the Roadmap gate before implementing the authorized slice. Analyst can prepare independent comparison/measurement work in parallel when ownership and dependencies are clear. A tiny correction may use the shared quick route only when every eligibility condition and inherited contract is recorded; an analytical improvement hypothesis does not establish that exemption.
5. Test & Code Review Engineer assesses the exact candidate's software and test effectiveness. Verifier independently assesses consequential measured-benefit claims, comparison validity and interpretation. Evaluate correctness and any claimed improvement separately. An implementation may meet its functional criteria while the expected benefit remains unproven.
6. Route concrete defects through the shared repair/reverification policy. If the implementation is sound but the hypothesis fails, return to analysis, retain/revert as authorized, or conclude; a valid negative result is not a failed defect repair.

Use substantive learning checkpoints for exploration and the named engineering phases/gates when promoting a change. Keep exploratory analysis in a form that fits the question; use shared canonical prefixes for engineering records that need durable handoff references. Transmit only relevant definitions and references in assignments. A metric is not automatically a gate; an acceptance criterion must define the threshold and method.

For requested benchmarks, distinguish the plan, inspected metadata, executed comparisons, analysis, and independent review. Execute the authorized benchmark or record the exact blocker and partial scope; metadata checks and a plausible explanation are not measured evidence. A valid negative result requires a valid executed method, not an unrun prediction. Requested execution remaining blocked prevents an overall completed claim.

## Outcome and handoff

Return a substantive analytical conclusion and discussion: what the evidence supports, competing explanations, comparison validity, uncertainty, consequences for the proposed design, and unresolved questions. Include the candidate change if any, actual execution/reproduction evidence, gate decisions, independent review scope, limitations, and next decision. State whether the result is exploratory, experimentally supported, accepted for a pilot, or ready for the named release boundary. A local benchmark or authored fixture is not evidence of production capacity or real-world prevalence. Move toward broader rollout only with the relevant acceptance evidence and existing release authority.

Follow the shared chat-first evidence contract: maintain canonical analysis, PRD, architecture, roadmap, and results in a specified working directory; summarize the conclusion and decisive numbers inline, using compact tables or visuals when useful. Link the canonical artifacts and attach a focused chart, data excerpt, or code/diff snippet when it improves inspection or reuse. Do not attach full raw datasets or duplicate reports in place of the explanation. Reuse valid artifacts rather than duplicating them across squads.
