# Build evidence that can change the decision

Use this reference to design checks, review coverage after implementation, and prepare an independent verification handoff.

## Select coverage by affected behavior and consequence

| Change or risk | Useful evidence | What would leave a gap |
| --- | --- | --- |
| Domain rule or state transition | Examples covering allowed and forbidden transitions; boundary inputs; invariants across a sequence | Only the happy path; asserting private helper calls |
| Defect correction | Reproduction on the original candidate and regression on the new one | Test passes on both revisions or fails for an unrelated setup reason |
| API/schema/consumer change | Contract checks, compatibility cases, real consumer path | Server-only tests while downstream interpretation changed |
| Persistence/migration | Representative data, interrupted migration/restart behavior, recovery rehearsal | Schema applies to an empty database only |
| Concurrent or retrying work | Duplicate, reordered, delayed, and concurrent operations against the actual storage/coordination mechanism | A sequential in-memory fake used to claim cross-process guarantees |
| Dependency failure | Timeout, partial response, unavailable dependency, retry/fallback limits | Every dependency mocked to succeed |
| Analytics/algorithm change | Known-answer cases, invariants, fair comparator, appropriate numerical tolerance | Expected outputs generated by the same algorithm under test |
| UI or operational journey | Real path through visible states, including empty/loading/error/recovery as relevant | Component snapshots alone establish workflow correctness |
| Performance or capacity | Representative workload, stable measurement definition, baseline, resource limits and uncertainty | Microbenchmark or single best run used as a deployment guarantee |

These are choices, not a required test matrix for every change. Explain an omitted material risk or a substituted check. Run project-required checks even when this matrix is narrower. A high coverage percentage cannot establish that meaningful cases or correct expectations were chosen.

Write actionable cases with preconditions, input/trigger, expected observable behavior, criterion, and command or procedure. Capture the revision and environment. Label results `passed`, `failed`, `not run`, or `blocked`; planned checks are not executed evidence. Environment failure is different from a product assertion failure.

Verify the current milestone's outcome as well as individual assertions. Use its accepted requirements, operating envelope and exit evidence. If a performance or accuracy threshold is unresolved, report the measured observation and the missing decision; do not invent a threshold after seeing the result or call the quality objective accepted. A local correctness fix that changes that envelope requires the corresponding design/acceptance decision to be revisited.

## Reconcile the design with what was built

After implementation, compare the actual diff and contracts with the intended criteria and tests. Trace each acceptance criterion to implementation and evidence. Identify new states, fields, branches, or dependencies that the original test design missed.

| Criterion | Implementation boundary | Evidence | Assessment |
| --- | --- | --- | --- |
| Criterion from the task | State transition method | Sequence test, command, candidate | Covered / gap / not delivered / blocked |

Coverage evaluation is a reasoning activity; it is not proof that tests ran. Keep review of test design separate from runtime results. Additional design concerns remain explicitly nonblocking unless they expose a real contract failure or the authorized owner changes the acceptance boundary.

## Independent verification and targeted repair

Give the verifier enough evidence to form an independent conclusion: task and criteria, exact revision/diff, requirements/design and gate scope, contracts, test commands and results, assumptions, and previous findings. Do not provide only a persuasive summary. Review contract quality, design fit and justified departures, failure handling, test sufficiency, and acceptance coverage. Add domain expertise when the consequence requires it; a role name does not supply that expertise. Use canonical artifact links and a substantive chat summary, with focused code/diff or result excerpts when they make the candidate easier to inspect. Do not attach the entire source tree or test log in place of relevant evidence.

The verifier returns `PASS`, `FAIL`, or `BLOCKED` for the named candidate and transition. Each blocking finding contains:

> **Finding / criterion:** violated behavior or unresolved consequential issue; preserve the caller's identifiers when supplied.
>
> **Evidence:** location, input, observed result, and reproduction conditions.
>
> **Consequence:** why the issue blocks this transition.
> **Owner and closure check:** who repairs it and the observable evidence that resolves it.

Suggestions are separate from blocking findings. Consolidate overlapping findings. The engineer repairs the problem and reruns affected checks; the verifier checks closure and plausible regressions. Do not rerun unrelated expensive evidence without a change or unresolved concern that justifies it. A reviewer who writes a substantive fix becomes an author of that fix; arrange another qualified check for it.

For the same problem, preserve each attempted repair and subsequent verification. Initial review, ordinary local red/green development, and exploration remain distinct from repair attempts. Apply the active task's stopping or escalation rule and retain history across reassignment. A changed approach needs a reason and remains within scope and budget; it does not erase previous evidence. The squad or task owner defines orchestration and retry limits, not this verification method.

Passing implementation checks does not establish a scientific conclusion or authorize an operational release. State which of those judgments were actually reviewed.
