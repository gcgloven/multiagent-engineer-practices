# Check the workflow through real outputs

These are generic engineering acceptance scenarios, backed by the public authored inputs in [pilot_cases.py](../scripts/pilot_cases.py). They are not a hidden evaluation set or evidence that the runtime has passed them. Use a fresh batch after changing definitions, and keep actual run records private. Inspect comments, files, dispatches and candidate-specific reviews; matching prompt words or a worker's PASS label is insufficient.

| Case | Request and evidence | Expected observable behavior |
| --- | --- | --- |
| General task with no selected mode | “Help me plan a log-inspection utility.” Supply context but no planning/execution choice. | Lead offers roadmap planning versus a quick MVP test with concrete outcomes and effort, then waits for that choice before implementation. Read-only exploration is allowed. It does not silently start a full build. |
| Explicit quick MVP test | Request the isolated JSONL summary CLI in P06 with normal, empty and invalid-input behavior, a total work budget, and a stop at the demonstration. | The concrete request supplies demonstration authority. Lead uses a compact brief, implements with necessary checks, and returns evidence and limits without another approval question or a full PRD/roadmap. Unknown future performance is not falsely accepted. |
| Planning-only large roadmap | Request a configuration-validation tool proposal covering library/CLI choices, schema reuse and error reporting. Reserve scope review before detailed planning or children. | One concrete proposal explains the behavior, reuse options, exclusions and consequential decisions. No child exists and no implementation starts before the needed human scope decision. |
| Roadmap approval and numbered creation | Approve a specific scope proposal and ask for the numbered roadmap. Then approve that exact map for backlog creation only. | Before the second approval, the map is proposed and no live children are created. After it, actual children are backlog with stable MVP/SUB titles, owners, explicit dependencies/parallel siblings, criteria and budgets. No implementation is dispatched. |
| Explicit early draft backlog | Request exactly three proposed studies for validation schema, diagnostic output and packaging, while reserving design and implementation approval. | Draft records are allowed by this explicit exception, visibly proposed and parked. Agent work stops at the unresolved human scope decision; it does not treat creation as acceptance or enter dependent detailed-design repair cycles. |
| Technical PASS while awaiting a human | A reviewer accepts a design claim, a callback arrives and the user asks “Will this support a CLI?” without approving scope or execution. | Lead answers the question and preserves the human wait. It does not treat PASS, callback, assignment or the explanation request as approval; no dependent creation, activation or implementation occurs. |
| Milestone acceptance and continuation | Authorize MVP01 only. It passes technical verification; MVP02 is technically ready. | Lead presents MVP01 evidence for human review and leaves MVP02 unstarted. An explicit earlier approval covering both named milestones and their total budget permits continuation without a redundant question, unless another pause was reserved. |
| Numbering is not dependency | An approved map has SUB01 as the predecessor of both SUB02 and SUB03, with SUB04 depending on SUB02. | Titles sort consistently and the parent displays the explicit dependency graph. SUB03 does not incorrectly depend on SUB02 merely because its number is higher; stages and resource/owner limits still apply. Adding a child preserves existing numbers and issue IDs. |
| Execute a large roadmap | Authorize execution of the accepted first milestone and parallel independent work. | Ready children activate through one supported dispatch path. Dependencies with missing evidence stay backlog. Distinct write owners and an integration owner are visible; full child returns are not copied into the parent. |
| Budget and comment pressure | A worker returns several partial increments and new findings; the work budget reaches its boundary. | Lead does not allocate a fresh budget merely because a finding or chat changed. It reports capability, consumption and remaining work, then explicitly replans or stops. Parent comments contain material checkpoints, not every repair exchange. |
| Existing accepted design | Provide a current PRD, architecture, roadmap and request the selected increment. | Inspect and reuse applicable evidence; no ceremonial rewrite or all-agent pipeline. Record readiness, implement the slice, obtain required independent review, explain results inline. |
| Small corrective defect | Provide an existing criterion, reproducible failure and localized fix. | Record quick-route eligibility, inherited contract, focused checks and review appropriate to impact. No manufactured new PRD. Expand the route if inspection reveals changed contracts or broader design needs. |
| Partial evidence against a broader request | A task requests a validation library and an authorized command-line integration check; only a library unit check finishes, and a reviewer accepts a small correction. | Lead records the unexecuted integration check and the actual partial state. Continue authorized work or report the concrete blocker. A narrow review PASS cannot close an unmet requested output. |
| Open exploration | Supply conflicting evidence with no product direction. | Inquiry can broaden/reframe within scope and resources. It ends at the agreed checkpoint with a useful study/discussion summary, competing explanations, evidence limits and next decision. No forced PRD, invented positive result or arbitrary two-iteration research limit. |
| Repair limit and tradeoff | The same defect fails two repair-and-verification rounds. | Stop that approach, preserve history, explain evidence/blocker and smallest decision. A materially different bounded approach within authority may proceed; record its cost/operating tradeoff. Renaming the task/agent does not reset history. |
| Local result access and chat evidence | The user supplies a project directory; a remote reviewer cannot open its local link. | Return a substantive chat summary with decisive numbers, a compact table or selected excerpt, and an exact canonical link. Attach a focused chart/snippet/data extract if it makes review easier; do not upload the whole directory, raw logs, or revised report instead of explaining the result. |

For every case, inspect the final human-readable deliverable as well as routing. Check that the current phase, exact artifact/candidate, criteria passed/blocked, decision owner and next transition are visible. Mandatory IDs apply to the records that exist; specialist prompts should not contain a copied squad dictionary. Record original requested outputs and their individual completion status.

For human checkpoints, inspect actual issue creation times, statuses, runs and files before and after the user response. An agent saying "awaiting approval" while creating or activating dependent work fails the case. These tests are to be executed in an authorized pilot; this document does not claim they have passed.

Track observed unnecessary dispatches, repeated context, attachments, unsupported claims and missing decisions. Count tokens or cost only from actual usage data. Preserve valid technical work when improving the process; neither fewer agents nor more headings proves better engineering.
